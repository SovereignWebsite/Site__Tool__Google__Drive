Scopes: what each gives and costs

A scope is the access Google asks you to grant. Pick the smallest that does the job. This page is the owner's decision record; the recommendation is at the end.

Drive scopes, as Google classes them (check Google's current scope table before relying on this)
ScopeWhat the app can doGoogle's classWhat it costs us
drive.file with the Google PickerOnly files and folders you pick for it, and files it creates. Browse, preview, download and upload inside those. It cannot list the rest of your Drive.Non-sensitiveThe OAuth consent screen and branding checks only. No restricted-scope review. Works for a team that shares one folder: each person picks it once.
drive.readonlyList and read every file in your Drive. No upload, no new folder.RestrictedGoogle's verification, and possibly an independent security assessment (Google's rule turns on whether restricted data can reach a server; a browser-only app may be treated differently, but only Google decides, so we would ask before building on it).
driveEverything above, plus change and delete anything in your Drive.RestrictedThe same review, and the highest risk to users if the page were ever compromised.
drive.metadata.readonlyFile names and metadata only, no content.RestrictedThe same review for less use.

What drive.file cannot do

  • It cannot browse your whole Drive. You open the Picker and choose what the app may use.
  • Picking a folder grants that folder. Files inside it that someone else put there may not be listed until you pick them too. A file the app creates in it is visible to the app.
  • A person who joins later has to pick the shared folder in their own browser. Sharing the folder in Drive is still done in Drive.

Which Google client signs people in

Google only returns a token to an origin registered on the OAuth client. The Gmail tool's client is Internal (one Google Workspace domain), so an outside team cannot use it. Options:

  1. Bring your own client id (the default for the API). Each importing site passes its own client id and registers its own origin. We hold nothing and carry no review. The cost is a few minutes of Google Cloud set-up per site.
  2. A separate External client for this site's own app. With drive.file only, it needs the consent screen and brand checks, not the restricted-scope review. With a restricted scope it needs Google's verification and, for a public client, a security assessment, which costs money and time. Spending that is Dinis's decision.
  3. A broker (a pop-up here handing tokens to other origins): not built. Any site could ask for someone's Drive. Only if security.b and Dinis say so.

The Google Picker is a Google script. Loading it puts Google's code in the page that holds the token and widens that page's script-src (the Gmail tool avoids this on purpose). The sign-in and every API call load no Google code; only the optional Pick button loads the Picker, on press. A site that wants to load no Google code can skip the Picker and use files the site creates itself.

Recommendation to Dinis

Ship with drive.file and the Picker. It is enough for the message channel (a lane is one shared folder that each person picks) and for a team that works in a few shared folders. It avoids the restricted-scope review altogether, and a page compromise exposes only what each person picked. Add drive.readonly only if people truly need to browse their whole Drive, and only after you decide to take on Google's review. Use option 1 for other sites and, for our own app, an External client with only drive.file. This app requests no restricted scope.
