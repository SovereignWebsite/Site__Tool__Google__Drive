Google Cloud set-up, step by step

This is a guide for someone who is not a developer. You make one thing in the Google Cloud console: a client, which is a name tag that tells Google "this website may ask people to sign in". It takes about fifteen minutes. Google renames its screens now and then; if a name below is not on your screen, look for the nearest one.

Only one thing leaves the console: the client ID

The sign-in here needs the client ID and nothing else. It looks like 123456-abc.apps.googleusercontent.com. It is public by design: it sits in the page's code. Google also shows a client secret when you make the client. You do not need it, never copy it, and never send it to anyone, us included. Nothing secret is ever sent to us.

Which case are you?

  • A. Our own Internal client. You administer a Google Workspace and make the client for this site (drive.google.tool.sovereignweb.site). Only people with accounts in your Workspace can sign in.
  • B. An outside team using the API on its own website. You make a client for your website, and your website imports the Drive API. Anyone with a Google account can sign in (External), or only your organisation (Internal).

The steps are the same for both. The differences are marked A and B.

Step 1. The project

  1. Open console.cloud.google.com and sign in. A: use an administrator account of the Workspace. B: use any account your team controls.
  2. At the top, click the project name, then New project. Name it, for example, Drive sign-in.
  3. A: under Organisation, pick your Workspace's organisation. An Internal client only works inside an organisation.
  4. Click Create, then make sure the new project is the one selected at the top.
  5. Menu, APIs and services, Library. Search Google Drive API, open it, click Enable. (Only if you will use the optional file Picker: also enable Google Picker API.)

Step 2. The consent screen

This is the page people see when they sign in. Menu, Google Auth platform (older consoles: APIs and services, OAuth consent screen). Click Get started and fill in:

  • App name: A: Sovereign Website Drive. B: your product's name.
  • User support email: your own address.
  • Audience: A: Internal. B: External for anyone with a Google account, or Internal if your whole team is in one Workspace you administer.
  • Contact email: your own address.
  • Branding (Google asks for these for External apps; fill them in anyway): Home page, A: https://drive.google.tool.sovereignweb.site/, B: your site's home page. Privacy policy, A: https://drive.google.tool.sovereignweb.site/app/privacy/, B: your own privacy page, which must say you do not keep Drive data. Authorised domain: A: sovereignweb.site. B: your site's domain.

Step 3. The scopes (what the app may do)

Menu, Google Auth platform, Data access, Add or remove scopes. Add only what you need. The most power you give is the most you risk if a page were ever broken into.

What each scope gives, and what it costs in Google's review (Google changes these rules; check its current page before relying on this)
ScopeWhat the app can doInternalExternal
drive.fileOnly files it creates or that the person picks.No review.Not a sensitive scope: no restricted review. Google may still check your branding.
drive.readonlyRead every file in the Drive.No review.Restricted. Google verifies the app, and a public app usually needs a yearly security assessment, which costs money. While the app is in Testing, up to 100 listed test users can use it with a warning screen, and no review.
driveRead, change and trash anything in the Drive.No review.Restricted, as above.

The full list of scope addresses is https://www.googleapis.com/auth/drive.file, .../auth/drive.readonly and .../auth/drive. If unsure, choose drive.file only. Which scope the owner of site A chooses is Dinis's decision (the trade-offs).

Step 4. The client (Web application)

  1. Menu, Google Auth platform, Clients, Create client.
  2. Application type: Web application. Name it anything.
  3. Authorised JavaScript origins, Add URI. A: https://drive.google.tool.sovereignweb.site. B: your website's address with no path, for example https://yourteam.example. It must be https, with no slash at the end.
  4. Authorised redirect URIs, Add URI. A: https://drive.google.tool.sovereignweb.site/app/connect/. B: the page on your site that finishes sign-in, for example https://yourteam.example/connect/, exactly as your code passes it as redirectUri. A slash at the end counts.
  5. Click Create. Google shows the Client ID and a Client secret. Copy the Client ID. Leave the secret alone.

Step 5. Where to paste the client ID

  • A: give the client ID to Dinis in his session, in these words: "a.drive, the client ID is [the ID]; commit it to site/app/config.js". It is a public value, so a chat message is fine. (An agent then puts it in site/app/config.js as clientId.)
  • B: put it in your own page's code: createDrive({ clientId: '[the ID]', redirectUri: location.origin + '/connect/' }). The examples are on the API page.
  • Optional, for the file Picker only: a browser API key restricted to your site (APIs and services, Credentials, Create credentials, API key) and the project number (project settings). The app works without them, on files it creates.

Step 6. Check that sign-in works

  1. Open the page (A: /app/connect/) in a normal browser window and press Connect with Google.
  2. Choose a Google account. For an Internal client, it must be in your Workspace.
  3. Google shows what the app asks for. Allow it. You should land on the Browse page with no error.
If Google shows an error
What it saysWhat it means
redirect_uri_mismatchThe redirect in step 4 is not exactly the one the page uses. Check https, spelling and the slash at the end.
origin_mismatchThe origin in step 4 is wrong or has a path or slash on the end.
org_internal or "only users in the organisation"The client is Internal and this account is outside the Workspace. Use an account inside it, or make the audience External.

Extra: the Chat tool (chat.google.tool.sovereignweb.site)

The Chat tool signs in the same way and can share the client you made in Step 4, in the same project. Add these. A: the Chat tool is for people in the same Workspace, so the Internal audience fits. Google Chat's API works with Workspace accounts.

  1. Step 1, last item: also enable Google Chat API (Library, search "Google Chat API", Enable).
  2. If Google asks you to set up the Chat API's configuration page (Google Chat API, Configuration), give the app a name such as Sovereign Website Chat and a short description, and leave the interactive features off. Google may or may not ask for this when people sign in as themselves.
  3. Step 3: add the Chat scopes .../auth/chat.spaces.readonly, .../auth/chat.messages.readonly and .../auth/chat.messages.create. Google changes its scope names, so pick the nearest ones from its list and tell the agent which.
  4. Step 4: on the same client, add the origin https://chat.google.tool.sovereignweb.site and the redirect https://chat.google.tool.sovereignweb.site/app/connect/.
  5. Nothing else changes: still only the client ID, and no secret. Do not create a key or a service account for the Chat tool; people sign in as themselves in their browser.
